## What's Changed

### Fix

- Normalize only ambiguous JSON request-fault markers on retryable 401/403/500–599 reports with matching plugin classes. CPA v8.0.32 ignores the plugin envelope's `Retryable` field and classifies the status/message instead: a generic request-fault marker could stop same-request credential failover. All four host-inspected locations (root, `error`, `response.error`, `body.error`) are checked, including simultaneous markers and case/whitespace variants. Specific request faults veto the entire rewrite. Duplicate object keys also preserve the whole body: Go maps keep the last occurrence whereas CPA's GJSON classifier reads the first, so collapsing duplicates could lose a specific fault or an upstream reason. Existing 402/429 and authentication/model-not-found handling, HTTP status, envelope code/retryable flag, upstream reason text, malformed/truncated bodies, network causes and post-emission failures stay unchanged. Only selected generic marker values change; error bodies are no longer promised byte-identical in those cases. No plugin-side key retry loop was added.
- Report why a catalog model was excluded, in the log message itself. Both post-refresh diagnostics (`unsupported models excluded from routable catalog`, `catalog normalization warnings`) used to carry their detail only in `host.log` fields, and the host's `LogFormatter` renders only its own field allowlist (`provider`, `model`, `error`, …) — every other key is dropped. The result on a live host was a line that repeated every refresh cycle with no model name and no reason, e.g. `unsupported models excluded from routable catalog`. The message now states the count and the `"<upstream id>": <reason>` pairs (plus normalization warnings) verbatim, so a snapshot that drops models is diagnosable from the log alone; upstream IDs stay `%q`-quoted, so CWE-117 log injection through control characters is still impossible. Diagnostics that repeat unchanged keep the previous cadence: one line per refresh.
- Reconcile CPA auth records against `api-keys` in both directions, so a key removed from the config stops being scheduled. Materializing keys into auth files was one-way: a removed key's record stayed enabled, and CPA kept offering it — on a live host the removed key returned `401 Invalid credential` on every 30-minute cooldown while the config held a single key. Registration and reconfigure now read each managed record's physical JSON (`host.auth.get` by runtime index), prove ownership (type, canonical `opencode-go-key-<sha256>` id, `api_key` hashing to that id), then **delete** an unconfigured record or re-enable a configured one. Deletion is a two-step operation, because the ABI exposes list/get/save but no delete: the record is saved as `disabled: true` (the host holds that state, and its filestore refuses to recreate a disabled credential whose file is gone) and the file is then unlinked, after which the host's auth-directory watcher unregisters the credential. The disable step is what makes the deletion stick: a bare unlink was rewritten from the host's in-memory credential on the next state change — observed live, where the resurrected key answered 401. The unlink is bound to the proof: the listing path and the read path must agree, the file is renamed to a unique non-`.json` sibling and proven from those bytes (type, canonical id, `api_key` digest), and only then is it disabled and removed — so the inode that was proven is the inode that is deleted. The file the host writes back is re-read and re-checked before it is unlinked, a file that fails any check is renamed back before anything is written, and a rollback links the record back without overwriting (reporting its recovery path if that name is taken). Prove-then-delete cannot be made atomic against another process rewriting the auth directory through this ABI; what is guaranteed is that the plugin only ever deletes a file whose bytes it has just verified as its own. Only an enable patch rewrites a record, and it changes only `disabled` (all other fields carried over as raw JSON). A path that cannot be proven is reported as a `warn` and left alone. Unrelated records and runtime-only credentials are never touched, and no write happens when the physical and runtime state already match, so repeated reconfigures are save-free. A host that has not attached its auth manager yet lists from disk without indices: creation still runs, existing-record changes are reported as deferred and finished by the next reconfigure. A save that outlives its deadline is treated as an unknown commit — the bridge keeps it counted as outstanding, so the next reconciliation waits for it to settle before reading or writing and otherwise reports that instead of a state the orphan could still overwrite. Credential housekeeping is best-effort: a failed list, read, save or unlink is reported as a `warn` and registration continues, because a failed registration makes the host drop the plugin and takes every model of this provider off the air. List/get/save failures are sanitized and never echo host error bodies.

### Verification

- Error-report unit fixtures cover all four host paths, specific-fault vetoes, unchanged statuses, malformed/null/non-object bodies, unrelated large integers and preserved reason text. Executor tests cover non-streaming and refused-stream failures; refused streams close the upstream exactly once and emit no downstream content. Manual validation against the actual CPA source at `911f49c` passed 46 classifier fixtures and 12 conductor cases: original generic error reports stop at credential A; normalized reports try A then B and succeed, for 401/403/503 in both streaming and non-streaming modes. This is offline host-code validation with fake credentials, not a claim of credentialed multi-key production testing.
- `go test ./...`, `go test -tags debug ./...`, `go vet ./...` and `gofmt -l .` are clean. `internal/plugin/refresh_test.go` now pins the quoted message form (and the no-raw-newline property) instead of the dropped `models` field, and `internal/plugin/integration_test.go` decodes the `warn` payload and asserts the message carries both the exclusion reason and the duplicate-entry warning.
- A record that disappears between the listing and the read (the host keeps its runtime entry until the auth-directory watcher processes the unlink) is left alone and reported, not treated as a failure: that race is what dropped the plugin on a live host during the first deploy of this change.
- The deletion path is pinned by tests for a listing/read path disagreement, a file swapped for an unrelated credential after the host's read (refused with no write at all), a removal whose disable save the host refuses (the staged file goes back with its original contents), a canonical file that appears while that save is failing (the rollback does not overwrite it and the proven record is preserved with its path reported), and a canonical file replaced after a successful save (left in place, reported), an unconfigured record whose digest does not match its name (never removed), a configured key whose file vanished while the host still listed it (restored rather than skipped), and a simulated host state-persist that rewrites credentials from memory — which must not resurrect a removed one, with an enabled credential as the control that proves the simulation bites.
- `internal/plugin/auth_reconcile_test.go` runs the reconciliation against a file-backed fake that keeps physical JSON on disk, runtime disabled flags and auth indices: `{A,B} → {B}` deletes A's file and keeps B's, `{B} → {A,B}` re-enables while preserving operator metadata, disk/runtime disagreements are repaired in both directions, a disk-only listing defers without writing or unlinking, digest/id/runtime-only mismatches are never rewritten or removed, a non-regular path is refused, an untrusted listed id never reaches the log, list/get/save failures surface sanitized, a save that outlives its deadline blocks the next pass until it settles (and fails the pass if it does not), and manager restarts stay save-free. The suite also runs under `go test -race`.
- Deployed to a live CLIProxyAPI v8.0.32 host by replacing the loaded plugin binary and restarting. The catalog fix shows `unsupported models excluded from routable catalog (6): "omen-alpha": no route determined; …` instead of the bare sentence. Restoring the stale, unconfigured record by hand and restarting exercised the reconciliation end to end: disk-only registration passes reported `opencode-go credential reconciliation deferred for 1 record(s)`, the post-manager reconfigure logged `opencode-go credential 50b7a3fd6f2a removed: no longer listed in configured api-keys`, the auth directory was left holding only the configured record, CPA's client list dropped the credential, and no `401 Invalid credential` appeared. That run also exposed a failure mode this release fixes: the very next pass still saw the runtime entry, could not read the unlinked file, and failing registration made the host unload the plugin, so all 31 models vanished from `/v1/models`; the current build reports that as a warn (`not reconciled: host auth get failed`), keeps the provider registered, and serves `opencode-go/glm-5.2` with HTTP 200.

### Upgrade Notes

- Update from this fork's plugin-store source (or replace the plugin binary) and reload CLIProxyAPI.
- `api-keys` is now the single source of truth for credentials: registering or reconfiguring **deletes** the CPA auth record of a key removed from the config (the auth file is disabled and unlinked, and CPA's auth-directory watcher unregisters it) and re-creates the record when the key comes back. Records the plugin cannot prove it created — a different `api_key` digest, a different `id`/`type`, a runtime-only credential, or a path it cannot verify — are never touched. Deletion depends on CPA's auth-directory watcher being enabled (the default); without it the file is gone but the in-memory credential survives until the next reload.
- Error bodies are no longer promised byte-identical on retryable 401/403/500–599 with matching plugin classes: only ambiguous generic JSON request-fault markers are rewritten (root, `error`, `response.error`, `body.error`), so CPA can try another credential within the same downstream request. Specific request faults, model-not-found codes, 402/429, 400-class errors, malformed/duplicate-key bodies, HTTP status, envelope metadata and upstream reason text are unchanged, and no plugin-side key retry loop was added.
- Catalog diagnostics now name the excluded models and their reasons in the log message itself; a line whose content is unchanged still appears once per refresh.
- No configuration keys were added, removed or changed. Existing `api-keys` configurations keep working, and reconciliation performs no writes when the auth store already matches the config, so repeated reconfigures and host restarts stay save-free.
