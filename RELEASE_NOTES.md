## Unreleased

### Fix

- Report why a catalog model was excluded, in the log message itself. Both post-refresh diagnostics (`unsupported models excluded from routable catalog`, `catalog normalization warnings`) used to carry their detail only in `host.log` fields, and the host's `LogFormatter` renders only its own field allowlist (`provider`, `model`, `error`, …) — every other key is dropped. The result on a live host was a line that repeated every refresh cycle with no model name and no reason, e.g. `unsupported models excluded from routable catalog`. The message now states the count and the `"<upstream id>": <reason>` pairs (plus normalization warnings) verbatim, so a snapshot that drops models is diagnosable from the log alone; upstream IDs stay `%q`-quoted, so CWE-117 log injection through control characters is still impossible. Diagnostics that repeat unchanged keep the previous cadence: one line per refresh.
- Reconcile CPA auth records against `api-keys` in both directions, so a key removed from the config stops being scheduled. Materializing keys into auth files was one-way: a removed key's record stayed enabled, and CPA kept offering it — on a live host the removed key returned `401 Invalid credential` on every 30-minute cooldown while the config held a single key. Registration and reconfigure now read each managed record's physical JSON (`host.auth.get` by runtime index), prove ownership (type, canonical `opencode-go-key-<sha256>` id, `api_key` hashing to that id), then **delete** an unconfigured record or re-enable a configured one. Deletion is an unlink of the exact auth file the host reported, followed by the host's auth-directory watcher unregistering the credential, because the ABI exposes list/get/save but no delete. The unlink is bound to the proof: the listing path and the read path must agree, and the file is renamed to a non-`.json` sibling and re-read there, so what gets deleted is the inode whose record re-proves ownership (type, canonical id, `api_key` digest); a file that fails the check is renamed back untouched. Only an enable patch rewrites a record, and it changes only `disabled` (all other fields carried over as raw JSON). A path that cannot be proven is reported as a `warn` and left alone. Unrelated records and runtime-only credentials are never touched, and no write happens when the physical and runtime state already match, so repeated reconfigures are save-free. A host that has not attached its auth manager yet lists from disk without indices: creation still runs, existing-record changes are reported as deferred and finished by the next reconfigure. A save that outlives its deadline is treated as an unknown commit — the bridge keeps it counted as outstanding, so the next reconciliation waits for it to settle before reading or writing and otherwise reports that instead of a state the orphan could still overwrite. Credential housekeeping is best-effort: a failed list, read, save or unlink is reported as a `warn` and registration continues, because a failed registration makes the host drop the plugin and takes every model of this provider off the air. List/get/save failures are sanitized and never echo host error bodies.

## What's Changed

### Fix

- Attach the replayed chain of thought to every assistant message of its own turn. A Responses assistant turn can span several Chat Completions messages — one per assistant text message, plus the tool-call message that carries the calls — and the replay used to stop at the first one, so the message carrying `tool_calls` went out without `reasoning_content`: the shape a DeepSeek endpoint rejects with HTTP 400 `The reasoning_content in the thinking mode must be passed back to the API.` The turn's reasoning is now dropped only at a real boundary (a user, system or developer message, or the tool result that closes the turn), and a fresh reasoning item opens a new assistant output: it replaces the value and closes the open tool-call merge, so the calls after it carry the new chain of thought in their own message.
- The replay stays limited to the `deepseek*` family — `reasoning_content` keeps its `omitempty` tag and the merge flag is reset only when a reasoning item is actually replayed — so every other Chat Completions-routed model (`glm*`, `kimi*`, `mimo*`, `hy*`, `longcat*`) keeps the exact wire shape of earlier releases. An input message without content (an empty `user`/`system`/`developer` item) also no longer splits a merged tool-call message, for any family. The Anthropic Messages route needs no change: one Anthropic turn is already one Chat Completions message.

### Performance

- Decode each typed source representation at most once per request. Session-ID derivation and the adapter conversion used to parse the same inbound body independently, so a cross-format request paid for two full typed decodes before the upstream call was even opened. A request-local lazy cache now serves both: nothing is decoded until a getter is called, each getter memoizes its value and its translation failure behind its own ready flag (so "decoded to nil" stays distinct from "not decoded"), and the Responses envelope and its input items are cached separately so the existing validation order is preserved. The body is decoded at most once per representation and is never rewritten; native passthrough still forwards the raw bytes, and no request becomes valid or invalid that was not already. Measured on a 7.28 MB Responses body this removes roughly 16 ms of pre-upstream work — more on the `deepseek*` chat-completions route, less on traffic that already carries a session header, because `resolveOpenCodeSessionID` short-circuited there before the fallback decode ever ran.
- `debugBodyMeta` no longer parses the request body. In `-tags debug` builds — which `CONTRIBUTING.md` recommends for local development — it ran a full generic `json.Unmarshal` of the body on the request path purely to log a length (about 20 ms at 7.28 MB) and echoed body first/last/error bytes that can carry credentials. It now records the byte length only.

### Why

The DeepSeek endpoints require the replayed chain of thought on the message that carries the tool calls, and the split-turn shape is not rare: any assistant turn that emits text before its calls produces it, as does this proxy's own Responses stream conversion, which assigns output indices in arrival order — a Chat Completions upstream that streams `reasoning → tool → text → tool` hands the client exactly that order.
